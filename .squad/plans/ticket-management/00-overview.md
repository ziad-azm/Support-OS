## Dependency notes

This feature maps to **EPIC 4 — Ticket Management** in `SupportOs backlog.MD` (lines 308-350). It depends on customer-management's `CUST-1` (Story 10) and authentication-authorization's `AUTH-2` (Story 09), both complete — see [`../customer-management/00-overview.md`](../customer-management/00-overview.md) and [`../authentication-authorization/00-overview.md`](../authentication-authorization/00-overview.md).

`TKT-1` (story 12) → `TKT-2` (Categories & Priorities, story 18) / `TKT-3` (Assignment, story 22) / `TKT-4` (Status & Escalation) → `TKT-5` (Ticket History). TKT-2, TKT-3, and TKT-4 each depend only on TKT-1 and can be sequenced in any order; TKT-5 is the natural last piece (a reusable activity-log pattern other epics can reuse). **TKT-3 is also the gate on two EPIC 6 stories** — `AGENT-1` (Agent Queue, `SupportOs backlog.MD:413-416`) and `AGENT-4` (Auto-Assignment Rules, lines 471-474) both list it as a dependency, which is why story 22 deliberately stops at a filter on the existing list rather than building a queue screen or any routing logic.

**Story 12 is the second feature domain in the project**, after customer-management, and the first to cross a feature boundary: its ticket form needs read-only customer data, which `CONVENTIONS.md` §15's `no-restricted-imports` rule forbids importing from `features/customers` directly. It resolves this by calling the `/customers/` backend endpoint directly from its own `api/` layer with a minimal local type (`CustomerOption`) — documented as the worked example in `CONVENTIONS.md` §23 and `frontend/src/README.md`.

**Scope boundary inside EPIC 4.** Four sibling stories own most of what a "ticket" eventually needs, and story 12's model is deliberately the CRUD core plus two placeholder fields only:

| Owned by | What |
|---|---|
| TKT-2 (line 322) | `Category` model, real priority management, category/priority filters |
| TKT-3 (line 329) | `assigned_agent`, assign/reassign, "my tickets" |
| TKT-4 (line 336) | Status-transition validation, escalation level/flag, the status-control UI |
| TKT-5 (line 343) | `TicketActivity` log, history timeline |

So story 12's `Ticket` has `status`/`priority` as bare placeholder fields (no transition rules, no management API) and **no status-changing UI at all** — TKT-4 owns that surface, and building a throwaway one now would be immediately superseded.

**A verified forward decision from Story 10, now resolved.** Story 10's own plan named `Ticket.customer`'s `on_delete=PROTECT` as the reason `Customer` needs no soft-delete flag. Story 12 implements that FK and, as a direct consequence, discovers and fixes a real gap: `apps/core/exceptions.py` had no handling for Django's `ProtectedError`, which would otherwise make `DELETE /api/customers/<id>/` 500 on any customer with tickets. Fixed in the **shared** exception handler, not ticket-specific code — verified live against the project's other `PROTECT` relation (`accounts.Role`/`User.role`) before this story, which had never exercised the gap because no API deletes a `Role`.

**Router collision, also resolved.** `apps.customers.urls` already mounts a `DefaultRouter` at the API root (`/api/`, established by Story 10). A second `DefaultRouter` for tickets at the same mount point would silently shadow part of it. `apps/tickets/urls.py` uses `SimpleRouter` instead, which generates no root view — Story 10's own plan named this as the documented alternative, for a different original reason (keeping the enveloped 404 at `/api/`).

**Note on testing:** per standing project policy this project authors no automated tests. Story 12 adds none. Its checks are the backend's `manage.py check`/`test`/`ruff`, the frontend's `lint`/`format:check`/`check:rtl`/`build`, an `en`/`ar` key-set comparison, real HTTP across four verbs × three permission states (including the `ProtectedError` fix in both directions), and a bilingual walkthrough of the list, detail, and form.

**Story 18 (TKT-2, Categories & Priorities) adds the `Category` model the backlog named as this story's job**, plus the project's first nullable foreign key (`Ticket.category`, `on_delete=SET_NULL` — a third FK-deletion pattern alongside `PROTECT`/`CASCADE`, chosen because a category is a classification tag, not an identity or a parent). `priority` itself was already real since Story 12; this story's "priority... with management endpoints" (intake) is satisfied by `Category`'s CRUD, reusing `tickets.*` permissions with no new constants (the intake's own "Reuse `AUTHZ`" instruction) and no new grant migration. It is also the first story to add equality-filter dropdowns to a list screen — `TicketListPage`'s category/priority filters are plain, locally-stated `Select`s (the `LanguageSwitcher` pattern) merged into the query params the same way free-text `search` already is, a new `CONVENTIONS.md` §19 pattern future filtered list screens (e.g. TKT-3's "my tickets") can reuse.

**Story 22 (TKT-3, Assignment) is that reuse** — its "Only my tickets" toggle is § 19's second consumer, and `Ticket.assigned_agent` is the fourth use of `SET_NULL` (after `Ticket.category` and Story 21's two author FKs), now a settled pattern rather than a decision. Three things in it are worth knowing before touching this area again:

- **There is still no user-listing API, and this story deliberately does not add one** — `SEC-1` owns user admin. Instead it adds a narrow `GET /api/tickets/assignable-agents/`, gated on `tickets.view`, whose queryset (`apps/tickets/assignment.py::assignable_agents()`) mirrors `permissions_for`'s own two branches in SQL: `is_superuser` **or** a role whose `permissions` JSON contains `tickets.manage`. Verified live against this project's Postgres — the JSON `__contains` lookup works and correctly includes the roleless superusers.
- **`assigned_agent` is read-only on `TicketSerializer`, writable only via `POST /tickets/<id>/assign/`.** Not ceremony: this project's forms send their full payload on every save, so a writable field would silently unassign tickets the day it entered `TicketInput`. The same action validates the target id against the *same* queryset the picker reads, so a hand-crafted request cannot assign a ticket to someone with no `tickets.manage`.
- **`GET /api/tickets/assignable-agents/` does not shadow `/api/tickets/<pk>/`** even though the detail route's `{lookup}` regex would match that literal string — DRF registers `detail=False` dynamic routes *before* the detail route, and Django resolves in registration order. Ordering, not the regex, is what makes it safe; story 22 verifies it explicitly rather than assuming.

**Story 23 (TKT-4, Status & Escalation) extends the same "field with its own action is read-only" rule to two more fields.** `status` (already a bare placeholder since Story 12) and two new fields, `escalated`/`escalated_at`, all move into `TicketSerializer.read_only_fields`, written only through two new actions: `POST /tickets/<id>/status/` (validated against a hand-authored transition graph in a new `apps/tickets/status.py`, the same small-pure-helper shape as `assignment.py`) and `POST /tickets/<id>/escalate/` (a manual boolean flag, not the automatic rule-driven escalation `SLA-3` will add later on top of a Celery foundation that does not exist yet). Both actions reject a no-op re-statement of the current value as a `400`, not a silent success — a new pattern this story adds to `CONVENTIONS.md` §23 alongside the read-only-action-field rule Story 22 established. The status control (`TicketStatusControl`) is an immediate-mutation `Select` with no confirm dialog, mirroring `TicketAssigneeControl` exactly; only the escalate/de-escalate button uses `useConfirm`, per a literal reading of the intake's "escalate action using shared confirm dialog" wording.

**Story 54 (SUPPORTOS-96, Category Management UI) is a post-EPIC-4 addition, not part of the original four TKT-2..TKT-5 sequence.** It closes the gap Story 18 deliberately left open — a frontend CRUD screen for `Category`, previously managed only via Django admin or direct API calls. It adds no backend model/API changes (the `CategoryViewSet` from Story 18 is reused as-is), only frontend screens plus a one-line correction to `CategoryAdmin`'s now-stale docstring. Its route/nav access is gated on `tickets.manage` for the whole screen (list included), mirroring `security-administration`'s `RoleListPage`/`RoleFormPage` pattern rather than the `tickets.view`/`tickets.manage` split the rest of this feature uses — there is no "read-only" tier for a management screen anywhere else in the app.

**Story 24 (TKT-5, Ticket History) is EPIC 4's last piece — a "reusable activity-log pattern" (the intake's own `🔑`).** A new `TicketActivity` model (generic `kind`/`from_value`/`to_value`, written only as a side effect of `assign`/`set_status`, never through its own request body) captures status and assignment changes; replies are read live from the existing `Message` rows instead of being duplicated, via `apps/tickets/history.py::build_history` — the same merge-two-querysets-into-one-feed shape `apps/customers/timeline.py::build_timeline` (Story 20) established, one app closer to home. The two `kind`s store fundamentally different value shapes on purpose: a status change stores the raw, still-translatable enum value, while an assignment change stores a resolved NAME SNAPSHOT (not a user id), so the audit trail survives the referenced user being deleted later — the standard "snapshot over live reference" audit-log tradeoff, now documented in `CONVENTIONS.md` §23. Escalation changes are deliberately not logged — the backlog's own task line names only status/assignment/replies, one story before escalation existed at all.
