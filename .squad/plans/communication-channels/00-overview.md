## Dependency notes

This feature maps to **EPIC 5 — Communication Channels** in `SupportOs backlog.MD` (lines 353-397). It depends on ticket-management's `TKT-1` (Story 12), complete — see [`../ticket-management/00-overview.md`](../ticket-management/00-overview.md).

`COMM-0` (story 13) → `COMM-1` (Email) / `COMM-2` (WhatsApp) / `COMM-3` (Live Chat) / `COMM-4` (SMS), each depending only on `COMM-0` and sequenceable in any order → `COMM-5` (Web Forms, story 19), which additionally needed `TKT-2` (Categories & Priorities — planned and implemented as ticket-management's story 18). EPIC 5 is now fully planned.

**Story 13 is the third feature domain in the project**, after customer-management and ticket-management, and reuses two patterns Story 12 established: `SimpleRouter` for every domain router after the first (`apps.customers.urls`'s `DefaultRouter` still owns the API root), and a child resource reusing its parent domain's permissions rather than inventing new ones (here, `Message` reuses `tickets.*` — no new permission constants).

**A placement decision worth reading before touching this feature again.** The intake's "Shared conversation UI" task sounds like it belongs in a `features/communications/` frontend folder matching the feature slug — story 13 deliberately does **not** create one. Its only real consumer is the ticket detail page (every channel renders through the *same* component there, which is the actual reuse the intake means — channel-agnostic rendering, not reuse across multiple screens), so the component lives in `features/tickets/components/TicketConversation.tsx`, calling `/api/messages/` directly the same way Story 12's `getCustomerOptions.ts` calls `/api/customers/` — a feature owning exactly the data shape it needs from another domain's endpoint, never importing that domain's frontend code (`CONVENTIONS.md` §15). The **backend** `Message` model still lives in `apps/communications/`, matching `backend/apps/README.md`'s app-purpose table.

**Scope boundary.** `Message` is deliberately minimal — `ticket` FK, `direction`, `channel`, `body`, `metadata` — and `ChannelAdapter` is an interface with zero concrete subclasses. COMM-1 through COMM-4 each provide exactly one real channel adapter; none of that is pre-empted here.

**Open question for whoever plans CUST-3 next (SUPPORTOS-30, Interaction History):** its intake lists `CUST-1, TKT-1, COMM-*` as dependencies. After story 13, both `Ticket` and `Message` exist as real, queryable models — whether "COMM-*" is satisfied by COMM-0's messaging spine alone or needs at least one real channel (COMM-1+) wired up is a product call story 13 does not make. **Story 14 (COMM-1, Email) now provides that first real channel**, if that reading is the one whoever plans CUST-3 next chooses.

**Story 14 (COMM-1, Email) adds the first concrete `ChannelAdapter` subclass and the registry COMM-0 deferred.** `apps/communications/adapters.py::register_adapter`/`get_adapter` is the minimal channel → adapter-class dispatch table, wired through `CommunicationsConfig.ready()`; `EmailAdapter` (`email_adapter.py`) is its first entry. `MessageViewSet.perform_create` dispatches every outbound message to whichever adapter is registered for its `channel`, catching and logging a send failure without failing the request — the pattern COMM-2 (WhatsApp), COMM-3 (Live Chat), and COMM-4 (SMS) each copy.

**Story 14 touches zero frontend files.** COMM-0's `TicketConversation.tsx` already offered `email` as one of five channel choices in its reply form — story 14's entire job is making the *backend* behind that already-existing choice real (an adapter that actually sends, and a webhook that actually receives), not building new UI.

**Provider config is `ENV`-only through story 14**, deliberately not pre-empting `INT-3` (Messaging Providers Config, `SupportOs backlog.MD:661-665`), which depends on `COMM-1/2/4` and is where a DB-backed credentials UI eventually replaces these environment variables.

**Story 15 (COMM-2, WhatsApp) is the second concrete `ChannelAdapter` and, unlike Story 14, engages the real provider's documented protocol directly** — Meta's WhatsApp Business (Cloud) API webhook verification handshake and `X-Hub-Signature-256` payload signing are implemented for real (both are pure, deterministic algorithms this project can fully verify without a live account), while the exact byte shape of a live inbound payload and whether a real outbound send succeeds remain explicitly unverified — the plan is honest about which claims are which. It also establishes two new patterns future channel stories reuse: routing by whatever identity a channel actually offers (here, `ContactDetail(channel="whatsapp")`, Story 11 — WhatsApp has no per-conversation address tag the way email's `+<ticket id>` does) instead of copying the previous channel's scheme unchanged, and refusing to run an outbound send at all against unconfigured settings (no safe "don't actually send" backend exists for an arbitrary HTTP call the way Django provides one for mail).

**Story 15 also carves the project's first (narrow, explicit) exception to the envelope-is-the-only-response-shape rule** (`CONVENTIONS.md` § 11) — Meta's webhook verification handshake requires a raw-text echo, not JSON, so a new `PlainTextRenderer` (`apps/core/renderers.py`) is used only for that one view's `GET` method.

**Story 15 touches zero frontend files**, same as Story 14 — `TicketConversation.tsx` already offered `whatsapp` as a channel choice since Story 13.

**Story 16 (COMM-3, Live Chat) is qualitatively different from every story before it: it is the first to touch shared infrastructure rather than adding an isolated adapter.** Adding Django Channels + Daphne changes how `manage.py runserver` itself boots — every prior COMM story was purely additive with zero risk to anything already shipped; this one is not. Its plan makes the regression pass (re-verifying every previously-shipped endpoint after the change) a load-bearing, explicit verification step, not an afterthought.

**Story 16 introduces the project's first real-time transport** — a per-ticket WebSocket group (Django Channels, in-memory channel layer, single-process scope by design — no Redis dependency exists in this project). `LiveChatAdapter.send()` (a normal, synchronous call from `MessageViewSet.perform_create`, unchanged since Story 13) bridges to the async channel layer via `asgiref.sync.async_to_sync`; the async `TicketChatConsumer` bridges back to synchronous Django ORM/adapter calls via `channels.db.database_sync_to_async` — both are Channels' own documented utilities, reusable by any future real-time feature (the backlog's AI-3 "Chatbot widget," which also "reuses conversation UI," is a candidate).

**Story 16 also introduces the project's first genuinely public, unauthenticated frontend surface** (`features/live-chat/`, route `/chat`, outside `RequireAuth`) — deliberately not built on `PORTAL-0` (`SupportOs backlog.MD:526-529`), which owns real customer authentication and is not yet planned. The widget's identity is a signed, unpersisted session token (`django.core.signing`, no new model, no new migration) scoped to one conversation, not a customer account — the same "lightweight anonymous identity" pattern any future anonymous surface (a chatbot widget, an embeddable web form for COMM-5) could reuse before reaching for `PORTAL-0`'s heavier machinery.

**Story 17 (COMM-4, SMS) is the third concrete `ChannelAdapter` engaging a real third-party protocol directly**, structurally closest to Story 15 (WhatsApp) but against Twilio's Programmable Messaging API rather than Meta's Cloud API — two concrete differences from WhatsApp shape the code: Twilio's inbound webhook is form-encoded (requiring a `parser_classes = [FormParser]` override on that one view, since the project's global `DEFAULT_PARSER_CLASSES` is JSON-only), and Twilio's `X-Twilio-Signature` is computed over the exact webhook URL plus every POST parameter rather than the raw body alone — pinned as an explicit `SMS_WEBHOOK_URL` setting rather than reconstructed from the request, so a reverse proxy or tunnel rewriting `Host` cannot silently break verification. Routing reuses `ContactDetail(channel="phone")` — the **existing** phone channel from Story 11 — rather than adding a redundant SMS-specific one, since a phone number is the same identity for SMS as for a voice contact.

**Story 17 touches zero frontend files**, same as Story 14/15 — `TicketConversation.tsx` already offered `sms` as a channel choice since Story 13.

**Story 19 (COMM-5, Web Forms) is the fourth concrete `ChannelAdapter` and the first that is inbound-only** — `WebFormAdapter.send()` unconditionally raises, since a web form has no delivery mechanism back to whoever submitted it, caught and logged by `MessageViewSet.perform_create`'s existing failure path (unchanged since Story 14). It is also the first channel to diverge from the "continue the customer's most recent non-closed ticket" routing rule Story 15/16/17 each reused: a web-form submission is a discrete, structured request, not a message in an ongoing conversation, so `WebFormAdapter.receive()` always creates a **new** ticket. Because it depends on `TKT-2`, it adds a second, narrower **public** view (`WebFormCategoriesView`) over the same `Category` table `CategoryViewSet` (Story 18) already exposes, rather than loosening that viewset's own `tickets.view` gate — a pattern any future public-facing read of an otherwise-authenticated resource can reuse. Its frontend (`features/web-form/`, route `/contact`) is the second anonymous, `RequireAuth`-free surface after Story 16's live chat, and is genuinely simpler: no session token, no WebSocket, a single submit-then-inline-success flow.

**Note on testing:** per standing project policy this project authors no automated tests. None of the six stories add one. Story 13's checks are the backend's `manage.py check`/`test`/`ruff`, the frontend's `lint`/`format:check`/`check:rtl`/`build`, an `en`/`ar` key-set comparison, real HTTP across four verbs × three permission states plus the required-filter guard, and a bilingual walkthrough of the conversation view including a manually-created inbound message. Story 14's checks are the same backend gates plus real HTTP against the inbound webhook (fail-closed with no token, first-contact ticket creation, tagged-ticket attachment, stale-tag fallback) and outbound dispatch verified against the local dev server's console-backend output. Story 15's checks add the verification handshake (including confirming the response body is genuinely plain text, not JSON), hand-computed HMAC signatures for both a valid and an invalid case, a non-text webhook event's silent `200`, and routing behaviour across an open vs. a closed prior ticket — none of it needs real WhatsApp credentials. Story 16's checks add a full regression pass across every prior endpoint after the Daphne switch, plus real WebSocket traffic (rejected/accepted connections on both auth paths, a customer message broadcasting to a connected agent, an agent's REST reply broadcasting to a connected customer) verified with a throwaway script using Channels' own `WebsocketCommunicator` test utility. Story 17's checks mirror Story 15's shape (hand-computed signature, first-contact/continuation/closed-ticket routing, outbound refusal when unconfigured) with a Twilio-specific hand-computed `X-Twilio-Signature` covering every sent parameter, plus a sanity check that the form-parser override is actually doing real work (a JSON `Content-Type` request against the same endpoint must fail). Story 19's checks confirm the public category list needs no auth, a submission creates Customer+Ticket+Message with and without a category, malformed/nonexistent category and missing-field rejections, that a repeat submitter's email reuses the customer but never the ticket, and that an outbound `web_form` send fails safely rather than crashing.
