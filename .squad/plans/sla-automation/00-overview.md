## Dependency notes

This feature maps to **EPIC 7 — SLA & Automation** in `SupportOs backlog.MD` (lines 450-490). It depends on `project-foundation-architecture`'s `FND-2` (Story 02, complete) — see [`../project-foundation-architecture/00-overview.md`](../project-foundation-architecture/00-overview.md).

**Story 27 (SLA-0, Background Jobs Foundation) is pure infrastructure — no `apps.sla` domain code at all.** It adds the shared Celery application (`config/celery.py`, sitting alongside `config/asgi.py`/`wsgi.py` as project wiring, not inside any app) and `django-celery-beat` as the database-backed scheduler. Redis is the local broker/result backend, installed as a local service exactly like PostgreSQL — never Docker, matching this project's existing "Docker optional, future" stance. `apps.sla` itself (already scaffolded, empty, in `INSTALLED_APPS`) gets its first real content in `SLA-1`.

**This story also unblocks `agent-workspace`'s `AGENT-3` (Tasks & Reminders)**, whose own dependency line names `SLA-4` (Alerts & Notifications) — `SLA-0` → `SLA-4` is the chain that needs to complete before `AGENT-3`'s "due notifications... trigger via shared notification system" task can be built for real, rather than against a system that does not exist yet.

**Story 28 (SLA-1, Response & Resolution Targets) does NOT depend on Story 27 (SLA-0)** — its own backlog dependency line names only `TKT-2`. SLA status is computed live on read (`apps/sla/policy.py::compute_sla_status`, reading `SLAPolicy` + `Ticket.created_at` + `Message`/`TicketActivity`), never persisted on `Ticket` and never evaluated by a scheduled job — no Celery task is needed until `SLA-3` (Escalation Rules) adds one. `SLAPolicy` config is Django-admin-only (`SLAPolicyAdmin`, the same "admin doubles as the config UI" call `CategoryAdmin` made in Story 18 for `Category`); the only new API surface is `GET /tickets/<id>/sla/`, gated `tickets.view` alone, feeding a new "SLA Status" card on `TicketDetailPage` — scoped to the detail page only, not the ticket list, to avoid an N+1 query cost across a paginated queue.

**Story 29 (SLA-2, Automatic Assignment) is the project's first real Celery consumer beyond Story 27's own `debug_task` smoke test.** `TicketViewSet.perform_create` fires `apps/sla/tasks.py::auto_assign_ticket.delay(ticket.id)` after saving a new ticket, wrapped in the same `try/except Exception: logger.exception(...)` resilience pattern `MessageViewSet.perform_create` (Story 14) already established for `adapter.send()` — ticket creation never fails or slows because of the assignment engine, even with Redis or the worker down. `AssignmentRule` reuses `SLAPolicy`'s (Story 28) two-tier category-specificity design verbatim, reading "category" from the intake's "rules (category/load/round-robin)" as the *scoping* dimension and `load`/`round-robin` as the two *selection* strategies within it — a documented interpretation, not an invented requirement. A new shared `apps/tickets/assignment.py::apply_assignment` helper now backs both the manual `assign` action (Story 22, refactored) and this story's automatic task, so the two paths can never drift on `TicketActivity` logging. Config is Django-admin-only (`AssignmentRuleAdmin`), the third `Category`/`SLAPolicy`-precedented "admin is the config UI" call this session.

**Story 30 (SLA-3, Escalation Rules) is the first story to actually use `django-celery-beat`'s own scheduling**, not just fire a task on demand (Story 29's `auto_assign_ticket.delay(...)`). It reads the intake's "at-risk/idle" as two independent triggers: at-risk reuses `apps/sla/policy.py::compute_sla_status` (SLA-1) directly (a ticket's response/resolution deadline is near and still pending); idle is computed from the most recent `Message`/`TicketActivity` timestamp, independent of any SLA policy. `apps/sla/tasks.py::evaluate_escalations` runs every 5 minutes via a `PeriodicTask`/`IntervalSchedule` pair seeded by a hand-written data migration (`0004_seed_escalation_schedule.py`) — the first use of the "data migration" option `CONVENTIONS.md` §24 already named — so the job is live the moment the story ships, while the `EscalationRule` criteria themselves stay opt-in, like `SLAPolicy`/`AssignmentRule`. The job is deliberately one-directional (escalates only, never de-escalates); a new `apps/tickets/escalation.py::apply_escalation` helper backs both it and the existing manual `escalate` action, mirroring Story 29's `apply_assignment`. Config is Django-admin-only (`EscalationRuleAdmin`), the fourth `Category`/`SLAPolicy`/`AssignmentRule`-precedented "admin is the config UI" call this session.

**Story 31 (SLA-4, Alerts & Notifications) is the shared notification service the intake describes as "reused by tasks, collaboration, SLA, AI."** A new `apps.notifications` app adds `Notification` (in-app record) and `apps/notifications/services.py::notify(...)` — the single entry point every event source calls — plus in-app delivery (the row itself, pushed live over a per-user Channels group, mirroring Story 16's `LiveChatAdapter`/`TicketChatConsumer`) and email delivery (`apps/notifications/tasks.py::send_notification_email`, the project's second `@shared_task` module, reusing Story 14's existing `EMAIL_BACKEND`/`DEFAULT_FROM_EMAIL` wholesale). It wires into exactly two event sources — ticket assignment and ticket escalation — because both already have a single shared helper (`apply_assignment`, Story 29; `apply_escalation`, Story 30) covering their manual and automatic trigger paths at once; "new message" and a separate "SLA at-risk" kind are deliberately deferred (no single existing chokepoint for the former, no persisted at-risk-but-not-escalated state for the latter — see Story 31 `## Prerequisites`). A known, accepted limitation: `CHANNEL_LAYERS` is still `InMemoryChannelLayer` (single-process, Story 16's own scope limit), so a notification raised from the Celery worker process (the automatic assignment/escalation paths) is created and emailed correctly but never pushed live to an open browser tab — only the manual (HTTP-synchronous) paths push live; the frontend's dropdown compensates by invalidating on every open rather than trusting the socket alone. `NotificationViewSet` is the first viewset to deliberately not extend `apps.core.views.BaseModelViewSet`: notifications have no create/update/destroy surface and no domain permission to gate, so it is `ListModelMixin`+`RetrieveModelMixin`+`GenericViewSet` with `IsAuthenticated` only — no new `Permissions` constant. The frontend adds a `NotificationBell` in `RootLayout`'s header (bell + unread badge + dropdown + mark-read/mark-all-read) and a live-toast socket hook mirroring `useTicketChatSocket`.

**`sla-automation` (EPIC 7) is now fully planned end-to-end, Stories 27-31.** Per `SupportOs backlog.MD` lines 483-489, `SLA-4` was its last remaining story. This also unblocks `agent-workspace`'s **`AGENT-3` (Tasks & Reminders)** and **`AGENT-5` (Team Collaboration)**, both previously blocked on this shared notification service — either is now immediately plannable.
